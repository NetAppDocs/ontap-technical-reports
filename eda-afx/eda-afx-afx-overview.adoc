== ONTAP personalities

AFX nodes run ONTAP with a special node personality called "AFX." You can verify the personality of nodes in a cluster w
with the following CLI command:

----
node show -fields personality
----

A node with the AFX personality returns `AFX` in the personality field. Mixing AFX nodes with unified ONTAP nodes in the
e same cluster is not supported. All nodes in an AFX cluster must run the AFX personality.

== Disaggregated architecture

Traditional all-flash systems couple compute and storage tightly. Controller pairs own specific disk shelves. When a wor
rkload needs more IOPS or throughput, a customer must add a full HA controller pair, which brings additional capacity reg
gardless of need. When a workload needs more raw capacity, adding shelves to an existing controller pair eventually exhau
usts that pair's processing headroom.

EDA creates exactly these imbalances: scratch workloads are compute-intensive while cold project archives are capacity-i
intensive. The same cluster that needs 32 nodes to sustain peak metadata rates during a tapeout sprint may need only 8 no
odes to handle the steady-state throughput during a design ramp.

AFX separates the compute and capacity dimensions:

* *Compute nodes* handle NFS and S3 protocol termination, ONTAP metadata services, inline deduplication and compression,
, encryption, and data services. Adding nodes increases throughput, IOPS, and metadata processing capacity.
* *Drive shelves* hold NVMe SSDs and provide raw capacity and disk-level bandwidth. Adding shelves increases usable capa
acity and aggregate sequential bandwidth.

Each resource type can scale independently. An organization can expand node count to handle a higher concurrency phase o
or expand shelf count to accommodate a larger design dataset, without over-provisioning the complementary resource.      

== Storage Availability Zone

The Storage Availability Zone (SAZ) is the single most architecturally significant difference between AFX and unified ON
NTAP. In unified ONTAP, each HA controller pair owns specific disk aggregates, and volumes reside within those aggregates
s. Data mobility between nodes requires copying data from one aggregate to another.

AFX replaces that model with the SAZ: a single shared pool that encompasses all drives in the cluster. Key properties of
f the SAZ:

* *No node disk ownership.* All AFX nodes can read and write to any drive in the SAZ. There is no concept of "this shelf
f belongs to this controller pair."
* *No physical aggregates.* ONTAP internally manages capacity borrowing and returning at the cluster level. Administrato
ors create and manage volumes, not aggregates.
* *Zero-copy volume moves.* Because all nodes share the same SAZ, moving a volume from one node to another does not requ
uire copying data. The metadata pointer changes; the blocks stay in place. This eliminates the multi-hour data copy opera
ations that volume moves require in unified ONTAP.
* *Global deduplication domain.* As of ONTAP 9.19.1, the SAZ enables deduplication fingerprints to be shared across all 
 volumes and all nodes in the cluster simultaneously.

You can view SAZ status with the following CLI command:

----
storage availability-zone show
----

== NVRAM replication

In unified ONTAP, NVRAM is physically connected between HA pair nodes. Write acknowledgment to the client requires that 
 the data be present on both NVRAM modules in the HA pair, which requires the two nodes to be in close physical proximity
y — typically adjacent in the same rack or adjacent racks with short NVRAM interconnect cables.

AFX moves NVRAM replication to the backend cluster network. Write data is replicated to a partner node over the same 400
0GbE backend fabric that carries all other cluster traffic. This change has two practical implications for EDA infrastruc
cture planners:

. *Flexible rack placement.* AFX HA pair nodes no longer need to be physically adjacent. They can be separated up to the
e maximum Ethernet distance supported by the backend fabric, enabling more flexible datacenter topology.
. *Backend network dependency.* The backend network carries NVRAM replication traffic in addition to data traffic. The b
backend switch design — 400GbE Cisco Nexus with 4x100GbE breakout cables per node — must account for this combined load. 

== RAID group improvements

AFX introduces significantly larger RAID group sizes compared to unified ONTAP. This change has direct implications for 
 usable capacity efficiency.

[cols="2,2,2,2",options="header"]
|===
| Platform | Max drives per RAID group | Parity + spare | Data drives

| Unified ONTAP
| 28
| 3 parity + 1 spare
| 24 data drives

| AFX
| 96
| 3 parity + 1 spare
| 92 data drives

|===

The practical impact is significant. With 84 drives loaded with 15.3TB NVMe SSDs:

* *Unified ONTAP:* Three RAID groups of 28 (with remainder): approximately 1,101.6TB usable
* *AFX:* One RAID group of 84 drives (within the 96-drive limit): approximately 1,224TB usable

AFX provides more usable capacity from the same drive count. Rebuild operations also benefit: because the SAZ pools all 
 nodes together, a drive rebuild can spread its I/O across all nodes in the cluster rather than being constrained to the 
 two nodes in the owning HA pair.

== Deduplication improvements

=== Before ONTAP 9.19.1

In AFX 9.18.1, deduplication operates at the volume or node level. A 10GB PDK cell library stored in four separate volum
mes across four different nodes is deduplicated within each volume, but the same 10GB file consuming space in all four vo
olumes results in 40GB total on-disk consumption across the cluster.

=== Global deduplication in ONTAP 9.19.1

ONTAP 9.19.1 introduces SAZ-level global deduplication. Deduplication fingerprints are now shared across all volumes and
d all nodes in the entire cluster. The same 10GB PDK cell library stored in four separate volumes consumes only 10GB on-d
disk cluster-wide, regardless of which nodes or volumes hold the duplicates.

For EDA environments that maintain multiple copies of the same tool installation or PDK across separate SVMs or volumes 
 for isolation purposes, global deduplication can reduce the on-disk footprint of those shared datasets dramatically. Too
ol trees that are nominally 1TB in total volume allocation may consume a small fraction of that on disk if the tool binar
ries are highly duplicated across volumes.

== Hardware

=== AFX 1K nodes

The AFX 1K is the compute node for AFX clusters. It is based on the AFF A1K platform, in a 2U rackmount form factor with
h no on-board storage drives. Node specifications relevant to EDA sizing:

* *Sequential read performance:* approximately 35GB/s per node
* *Sequential write performance:* approximately 10GB/s per node
* *Backend connectivity:* 4x100GbE breakout cables to 400GbE backend switches

These per-node figures scale with additional nodes up to the 32-node cluster limit.

=== NSM140 drive shelves

AFX uses NSM140 NVMe drive shelves. Each shelf carries up to 24 NVMe SSDs and provides 16x100GbE RoCE Ethernet ports for
r backend connectivity. The back-end network uses 400GbE Cisco Nexus switches.

Shelf performance (per shelf):

* *Sequential read:* 140GB/s (TLC drives and QLC drives deliver equivalent read bandwidth)
* *Sequential write:* 70GB/s (TLC drives); 35GB/s (QLC drives)

The node-to-shelf saturation ratio in ONTAP 9.19.1 is approximately 4:1. Four nodes can fully saturate a single shelf's 
 read bandwidth. This ratio should inform the balance of nodes and shelves in an EDA cluster design.

AFX clusters support up to 25 shelves per cluster as of ONTAP 9.19.1RC1. This limit has increased across releases:      

* 9.18.1GA: 12 shelves
* 9.19.1RC0: 17 shelves
* 9.19.1RC1: 25 shelves

== Feature caveats for EDA deployments

AFX is a purpose-built platform and trades some unified ONTAP capabilities for its architectural advantages. Before desi
igning an AFX deployment for EDA, infrastructure teams must be aware of the following capabilities that are *not availabl
le* on AFX:

[cols="2,3,3",options="header"]
|===
| Feature | Availability on AFX | EDA Impact and Alternative

| Block protocols (FCP, iSCSI, NVMe-oF)
| Not supported
| EDA is an NFS workload. No practical impact for EDA environments that use NFS exclusively.

| FabricPool
| Not supported (aggregate-dependent)
| Cold data tiering from AFX-hosted volumes is not available. Use SnapMirror to replicate cold data to a Tier 2 AFF C-Se
eries or FAS system, which then uses FabricPool to tier to object storage. See xref:eda-afx-storage-design.html[Storage d
design].

| MetroCluster
| Not supported (aggregate-dependent)
| Replace with SnapMirror Active-Sync for NAS (introduced in ONTAP 9.19.1GA) for synchronous, near-zero RPO protection o
of NAS data. See xref:eda-afx-data-protection.html[Data protection].

| ZAPI
| Not supported
| Use the ONTAP REST API for automation and integration. Most ONTAP tooling that used ZAPI has been updated to REST API.

| NetApp ActiveIQ Unified Manager
| Not supported
| Use Grafana Harvest (version 25.11.0 or later) for monitoring and alerting. See xref:eda-afx-best-practices.html[Best 
 practices].

| Copy-based volume moves
| Not available (replaced by zero-copy moves)
| Not a limitation — zero-copy volume moves are faster and simpler. No customer action required.

| NFS copy offload for virtualization
| Not available on FlexGroup with Granular Data Distribution
| Limited impact for EDA environments; EDA workloads do not rely on NFS copy offload.

|===

IMPORTANT: FabricPool is not supported on AFX. Any documentation or guidance that references FabricPool tiering from AFX
X-hosted volumes is incorrect. Cold data archival from AFX requires SnapMirror replication to a Tier 2 system that suppor
rts FabricPool.

== Management tools

AFX clusters are managed through the same toolset as unified ONTAP, with a small number of additions and exceptions.    

=== Supported management tools

* *ONTAP CLI:* Nearly identical to unifiedONTAP. New `dcn` and `data-engine` command directories support AFX-specific A
AIDE (Autonomous Infrastructure Design Engine) operations.
* *ONTAP System Manager:* Nearly identical GUI experience with AFX-specific additions, including a new cabling view for 
 the backend network topology.
* *ONTAP REST API:* Full REST API support with exceptions for aggregates, MetroCluster, SAN protocols, and some performa
ance counters that are not applicable to AFX.
* *Grafana Harvest:* Full monitoring support in version 25.11.0 and later. Recommended for EDA environments requiring pe
er-volume latency and throughput dashboards.
* *NetApp Trident:* Container storage integration supported in version 25.10 and later.
* *NetApp Console:* Supported for cluster management.

=== Not supported

* *NetApp ActiveIQ Unified Manager:* Not supported on AFX. Use Grafana Harvest for equivalent monitoring capability.    

NOTE: When integrating AFX with existing ONTAP automation scripts or infrastructure-as-code pipelines, verify that all a
automation uses REST API calls, not ZAPI. ZAPI is not supported on AFX.
