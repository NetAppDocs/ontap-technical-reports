= FlexGroup volumes and workspaces
:icons: font
:imagesdir: ./media

[.lead]
FlexGroup volumes are the primary volume type for EDA workloads on AFX. They distribute a single namespace across multiple constituent member volumes spread across all nodes and shelves in the cluster, enabling metadata rates and sustained bandwidth that no single-volume design can match. FlexClone provides near-instantaneous workspace provisioning that eliminates the hours of copy time that conventional workspace management requires.

== Why FlexGroup matters for EDA

The limiting factor for most EDA storage deployments is not raw disk throughput — it is the rate at which the storage system can process file metadata operations. File create, stat, readdir, open, close, unlink, and rename operations are the true bottleneck for job scheduler throughput.

When a job scheduler dispatches 500 simultaneous EDA jobs, each opening 1,000 library files in the first few seconds of execution, the storage system must process up to 500,000 metadata operations in a very short burst. A single FlexVol, backed by one node's CPU and memory, will saturate and introduce latency that the scheduler interprets as slow job starts or failed submissions.

A FlexGroup backed by 16 AFX nodes distributes that same metadata load across 16 parallel processing engines. The aggregate metadata capacity scales linearly with the number of constituent volumes, which in turn scales with node count. The result is a single namespace that an engineer or job scheduler sees as one mount point, but which internally parallelizes metadata across the entire cluster.

The SPEC SFS 2014_swbuild benchmark was designed specifically to model the software build workload that EDA infrastructure must sustain. FlexGroup volumes on ONTAP have demonstrated leading results in this benchmark. On AFX, where FlexGroup constituent counts can reach 512 in ONTAP 9.19.1RC1, the theoretical metadata ceiling exceeds any previously published ONTAP result.

== Advanced Capacity Balancing

In unified ONTAP FlexGroup volumes, constituent imbalance has historically been a challenge. Files are distributed across constituents based on a hashing algorithm. When large files are written, they can land disproportionately on a small number of constituents, creating hotspots where some constituents are nearly full while others have substantial free space. The `volume rebalance` command can redistribute data, but it requires I/O overhead to do so.

AFX introduces Advanced Capacity Balancing, which is *enabled by default* on AFX FlexGroup volumes. Advanced Capacity Balancing changes the behavior for large files:

* Files larger than 10GB are written as *multipart files*, with parts distributed across multiple constituent volumes automatically.
* This eliminates the large-file constituent hotspot problem at write time, before imbalance can develop.
* Rebalance operations are still available but needed far less frequently.

For EDA workloads that produce large simulation result files (GDS files, netlists, timing reports), Advanced Capacity Balancing prevents the capacity drift that has historically required periodic administrative intervention on unified ONTAP FlexGroup volumes.

== Constituent sizing and limits

=== Constituent count recommendation

For maximum metadata throughput on AFX:

* Set the FlexGroup constituent count to a multiple of the node count in the cluster.
* A ratio of 8 constituents per node is a typical starting point for metadata-heavy EDA workloads.
* Constituent count should not exceed the FlexGroup constituent limit for your ONTAP version (see below).

Example: A 16-node AFX cluster would use 128 constituents per FlexGroup (16 nodes × 8 constituents/node). This gives 128 parallel metadata streams for a single-volume EDA namespace.

=== Constituent limits

*FlexGroup constituent limits by ONTAP version*

[options="header"]
|===
| ONTAP Version | Maximum FlexGroup Constituents
| Unified ONTAP (all versions) | 200
| AFX 9.18.1 | 200
| AFX 9.19.1RC1 | 512
|===

The 512-constituent limit in ONTAP 9.19.1RC1 is exclusive to AFX and significantly increases the metadata scalability ceiling for very large EDA deployments. A 32-node cluster using 512 constituents provides 16 constituents per node — a higher per-node constituent density that benefits workloads where metadata rates continue to scale with constituent count.

NOTE: The metadata throughput benefit of additional constituents is greatest when the constituent count allows each ONTAP node to host multiple constituents simultaneously. Monitor per-constituent utilization to verify that constituent load is well-distributed before increasing constituent count.

=== Capacity sizing

When sizing FlexGroup volumes on AFX:

* Size total capacity at least 1.5x the expected peak working set to provide headroom for Snapshots and deduplication bookkeeping.
* Account for global deduplication savings (ONTAP 9.19.1+) when sizing tool and library volumes that are likely to be duplicated across SVMs. Effective capacity consumption may be significantly lower than the provisioned volume size.
* Avoid placing multiple high-metadata-rate FlexGroup volumes on the same set of nodes if their combined metadata rate approaches the per-node processing limit.

=== Monitoring constituent health

Use the following ONTAP CLI commands to monitor FlexGroup constituent utilization:

----
volume show -fields constituent-count,used,available
----

For more detailed per-constituent breakdown:

----
volume show -is-constituent true -volume-name <flexgroup-name>* -fields used,available,used-percent
----

TIP: Constituent imbalance beyond 15-20% difference in used-percent between the most and least utilized constituent is worth investigating. Advanced Capacity Balancing prevents large-file imbalance in AFX, but directory and small-file access pattern skew can still cause hotspots. Review NFS export policies and mount point distribution if imbalance appears.

== FlexClone for workspace provisioning

=== The workspace problem

EDA design teams require private workspaces where individual engineers or teams can modify files without affecting the shared project baseline. The baseline may include hundreds of gigabytes of design data accumulated over weeks or months: layout files, netlist data, simulation results, and configuration that represents the current known-good state of the design.

Historically, provisioning these workspaces meant copying the entire baseline to a new storage location. A 500GB workspace copy over NFS could take hours, blocking the engineer from starting work and consuming both storage capacity and network bandwidth for the duration.

=== FlexClone mechanics

FlexClone creates a writable clone of a FlexGroup or FlexVol volume instantaneously. The clone operation creates a metadata copy that shares physical data blocks with the parent volume. No data is copied at clone creation time.

* A clone of a 500GB volume completes in seconds regardless of volume size.
* The clone initially consumes essentially no additional storage — it references the parent's blocks.
* As the engineer writes to the clone, only the modified or new blocks are written to new storage (copy-on-write). Blocks that the engineer has not touched continue to share storage with the parent.
* For an engineer who spends a day reading from the baseline and making targeted modifications, the clone may grow by only a few gigabytes even after a full day of work.

For a team of 50 engineers each running daily FlexClone workspaces on a 500GB baseline, total clone storage might be 10–50GB of actual new data rather than 25TB of full copies.

=== Workflow for FlexClone workspaces

A recommended FlexClone workspace workflow for EDA:

. Maintain a designated *baseline volume* for each design project, protected by periodic Snapshots.
. When an engineer needs a workspace, create a FlexClone from the most recent approved Snapshot of the baseline:
+
----
volume clone create -vserver <svm> -flexclone <workspace-name> \
  -type RW -parent-volume <baseline-volume> \
  -parent-snapshot <last-approved-snapshot>
----

. The engineer mounts the FlexClone volume and works in isolation from other engineers and from the baseline.
. When the engineer's changes are reviewed and approved, they can be merged back to the baseline through the design team's source control workflow.
. The FlexClone workspace is deleted once changes are integrated, releasing space:
+
----
volume clone delete -vserver <svm> -flexclone <workspace-name>
----

=== Clone lifecycle management

Unconstrained clone growth can consume substantial storage over time, particularly if engineers accumulate stale workspaces that are no longer actively used. Apply a workspace lifecycle policy:

* Define a maximum workspace age (for example, 30 days) after which idle clones are automatically flagged for review.
* Use ONTAP CLI scripts or REST API automation to identify and report on workspaces that have not received writes in more than N days.
* Require engineers to periodically confirm active workspaces or have them recycled.

TIP: Configure Snapshot protection on FlexClone workspaces to give individual engineers their own recovery points. An hourly Snapshot with 24-hour retention gives engineers the ability to roll back accidental file deletions without requiring storage administrator intervention.

=== FlexClone performance characteristics

FlexClone workspaces deliver full performance from the first access:

* *Reads from unmodified blocks* are served from the same physical location as the parent, with no performance penalty. A simulation run that reads exclusively from the baseline design data performs identically whether it runs from the parent volume or a FlexClone of it.
* *First write to a shared block* triggers a copy-on-write, which adds one additional write I/O. For workloads that write heavily to new files (scratch output), the copy-on-write overhead applies only to blocks that the parent volume also holds, which decreases as the workspace diverges from the baseline.
* *Clone creation time* does not depend on volume size. A 5TB FlexClone completes in the same elapsed time as a 50GB FlexClone.
