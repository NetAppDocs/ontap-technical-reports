= Best practices
:icons: font
:imagesdir: ./media

[.lead]
The following best practices reflect deployment experience and design guidance for EDA workloads on AFX. They cover hardware sizing, volume configuration, NFS client tuning, security, data lifecycle, HPC scheduler integration, and monitoring. Each recommendation is specific and actionable; adapt them to your environment's particular workload profile and organizational requirements.

== Hardware design

* *Deploy AFX as Tier 1 storage* for EDA tools, PDKs, cell libraries, and performance scratch. Size the node count based on metadata throughput and sequential bandwidth requirements, not on capacity alone.

* *Size for peak concurrent job count,* not average load. EDA workloads spike sharply during tapeout sprints. An underpowered Tier 1 cluster during peak simulation load directly increases license consumption and delays tape-out.

* *Use the 4:1 node-to-shelf ratio* (ONTAP 9.19.1) as a starting point for clusters with balanced read/write profiles. Adjust toward more shelves for capacity-dominant workloads (cold project storage) or more nodes for metadata-dominant workloads (high concurrent job counts).

* *Use AFF C-Series or FAS for Tier 2.* These platforms support FabricPool, which is the correct destination for cold data migrated from AFX via SnapMirror. Right-size Tier 2 for build artifacts, home directories, source control, and the cold data pipeline from Tier 1.

* *Size the front-end storage network at 100GbE per node* for AFX clusters to avoid front-end network saturation on concurrent simulation jobs. A 16-node AFX cluster requires a front-end switch fabric capable of sustaining 16 × 100GbE simultaneously.

.AFX cluster switch fabric showing front-end 100GbE client ports and back-end 400GbE NVRAM replication ports
image::afx-cluster-switch-label.jpg[AFX Cisco Nexus switch port labeling for front-end and back-end fabric,align="center"]

* *Plan for 4x storage capacity growth per new chip design generation* when forecasting capacity requirements. Each process node step roughly quadruples the storage intensity of the design flow.

* *Use TLC drives for high-write volumes* (scratch, simulation results) and *QLC drives for high-read, high-capacity volumes* (tools, PDKs, completed project data). QLC drives provide excellent read performance at lower cost per terabyte; TLC drives provide better write throughput where needed.

== Volume configuration

* *Use FlexGroup volumes for all EDA datasets* that are accessed by HPC job scheduler compute nodes. Single FlexVol volumes will saturate their metadata capacity as job counts grow.

* *Set FlexGroup constituent count to a multiple of the node count.* A starting point of 8 constituents per node provides good metadata distribution. In ONTAP 9.19.1RC1, AFX supports up to 512 constituents per FlexGroup.

* *Advanced Capacity Balancing is enabled by default on AFX* — no configuration required. This prevents large-file constituent hotspots. Do not disable it.

* *Enable inline deduplication and compression on all volumes.* Library data and tool binaries deduplicate well. With global deduplication in ONTAP 9.19.1, tool trees shared across multiple SVMs consume minimal additional on-disk space.

* *Do not configure FabricPool tiering policies on AFX-hosted volumes.* FabricPool is not supported on AFX. Cold data lifecycle management from AFX must use SnapMirror to a Tier 2 system that supports FabricPool.

* *Use FlexClone for engineer workspace provisioning* instead of full copies. Enforce a maximum workspace age policy to prevent clone proliferation on the parent baseline volume.

*Volume configuration by dataset type*

[options="header"]
|===
| Dataset | Volume Type | Snapshot | Cold Data Management | Notes
| EDA tools | FlexGroup | Daily / Weekly | SnapMirror to Tier 2 at major tool version changes | Mount read-only with `nocto`; one volume per major tool suite version
| PDKs / Cell libraries | FlexGroup | Daily / Weekly + per-release | SnapMirror to Tier 2 at PDK version retirement | Retain per-release Snapshots indefinitely for re-spin support
| Performance scratch | FlexGroup | Per-run start, or disabled | Delete or SnapMirror to Tier 2 at job completion | High-churn; minimize Snapshot overhead for active jobs
| Project workspaces | FlexClone of baseline FlexGroup | Hourly | Delete clone when changes are integrated to baseline | Clone from last known-good baseline Snapshot
| Build artifacts | FlexGroup (Tier 2) | Daily | FabricPool 31-day cooling policy on Tier 2 | On Tier 2, not AFX; FabricPool tiers cold builds to object storage
| Completed project archives | FlexGroup or FlexVol (Tier 2) | Weekly + milestone | FabricPool 7-day policy on Tier 2; SnapMirror Cloud for long-term | SnapMirror from AFX to Tier 2 at project completion; Tier 2 handles FabricPool
|===

== NFS client tuning

Correct NFS client configuration has an outsized effect on EDA performance. The default Linux NFS settings are conservative and leave significant performance unrealized on high-bandwidth storage like AFX. The following guidance covers mount options, attribute cache tuning, read-ahead, and kernel parameters — organized by their impact on EDA workloads.

=== Mount options

Apply the following mount options on all HPC compute nodes mounting AFX volumes:

----
vers=4.2,nconnect=8,rsize=1048576,wsize=1048576,nocto,actimeo=600,tcp,timeo=600,retrans=2,trunkdiscovery
----

Rationale for each option:

*Mount options per volume type*

[options="header"]
|===
| Mount option | Purpose and EDA rationale
| `vers=4.2` | NFSv4.2 with ONTAP 9.18.1+ delivers 30% better sequential read performance than NFSv3 via MPIO support, and eliminates the metadata serialization bottleneck via Concurrent Open Close. Use NFSv4.2 for new deployments.
| `nconnect=8` | Allows 8 TCP connections per NFS mount. Testing (including SAS GRID at scale) showed `nconnect=8` delivers optimal performance — a 30% wall-clock runtime reduction vs. no nconnect. Values above 8 (up to the 16 maximum) provide diminishing returns for most workloads.
| `rsize=1048576,wsize=1048576` | 1 MiB I/O transfer size maximizes sequential transfer efficiency for library reads and scratch writes. Appropriate for AFX bare-metal ONTAP; validate against your specific application for mixed-size workloads.
| `nocto` | Disables close-to-open consistency for read-only library and tool mounts. Eliminates ~65–70% of unnecessary `getattr`/access round-trips to the server. *Use only on volumes where clients have read-only or exclusive ownership* — not on shared read/write scratch volumes.
| `actimeo=600` | Sets attribute cache TTL to 10 minutes. Combined with `nocto`, this reduces `getattr`/access calls by a further 20–25%. For EDA tool and library volumes that are updated infrequently (major version changes only), a 10-minute stale-attribute window is acceptable and the performance benefit is substantial: one large EDA site reduced tool-volume IOPs from >150,000 to ~6,000 using `nocto` + `actimeo=600`.
| `trunkdiscovery` | Enables NFSv4.1/4.2 session trunking. Allows a single NFS mount to automatically discover and use multiple AFX cluster LIFs, spreading I/O load across cluster nodes without requiring the client to manage multiple explicit mount points.
| `tcp,timeo=600,retrans=2` | TCP transport with generous timeout. Required for large-transfer high-throughput workloads. The 600-decisecond (60-second) timeout prevents premature connection tears under momentary congestion.
|===

IMPORTANT: `nconnect` and `sec=krb5*` must not be used together. The GSS-API security context is shared across all `nconnect` connections, and out-of-order packet delivery causes context invalidation and message replay — resulting in significant performance degradation. For security-sensitive volumes requiring Kerberos, use `sec=krb5p` without `nconnect`.

NOTE: All mounts from a single NFS endpoint (LIF IP address) inherit the `nconnect` connection count of the *first* export mounted from that endpoint. Always mount the primary volume first with the desired `nconnect` value; subsequent mounts from the same LIF will inherit it automatically.

=== Attribute cache tuning for read-only volumes

For EDA tool and library volumes that multiple clients mount read-only, `nocto` and `actimeo` together dramatically reduce unnecessary server traffic:

* `nocto` removes the requirement to validate file freshness on every open, reducing `getattr` calls by 65–70%.
* `actimeo=600` extends the attribute cache lifetime to 10 minutes, reducing the remaining `getattr` calls by another 20–25%.

The combined effect converts a tool volume that was generating 150,000+ IOPs in a large EDA environment to approximately 6,000 IOPs — a 25× reduction — with no change to application behavior.

For volumes where clients do write data (scratch, workspaces), use the default `cto` (close-to-open) consistency behavior. The close-to-open guarantee ensures that engineers see each other's committed changes when opening files, which is critical for collaborative design work. Do not apply `nocto` to shared read/write volumes.

*Attribute cache recommendations by volume type*

[options="header"]
|===
| Volume type | `cto` / `nocto` recommendation | `actimeo` value
| EDA tools | `nocto` — read-only, version-controlled updates | 600 (10 minutes)
| PDKs / Cell libraries | `nocto` — read-only, updated at controlled intervals | 600 (10 minutes)
| Performance scratch | `cto` (default) — actively written by multiple jobs | Default (30 seconds)
| Project workspaces (FlexClone) | `cto` (default) — individual engineer writes | Default (30 seconds)
| Home directories (Tier 2) | `cto` (default) | Default
|===

=== NFS read-ahead tuning

Modern Linux distributions (RHEL 8.3+, Ubuntu 18.04+) reduced default NFS read-ahead from 15× rsize to a fixed 128 KiB, regardless of the `rsize` mount option. With a 1 MiB `rsize`, this represents a 120× reduction from the historical default (15,360 KiB) and can visibly degrade sequential read performance for library and tool mounts.

Set read-ahead to 15,360 KiB for all AFX tool, library, and scratch volumes:

----
# Set read-ahead dynamically for a specific mount point
./readahead.sh set /mnt/eda-tools 15360
./readahead.sh set /mnt/eda-libs 15360
./readahead.sh set /mnt/scratch 15360
----

Persist read-ahead across reboots using a `udev` rule in `/etc/udev/rules.d/99-nfs.rules`:

----
SUBSYSTEM=="bdi", ACTION=="add", \
  PROGRAM="<absolute_path>/awk -v bdi=$kernel \
    'BEGIN{ret=1} {if ($4 == bdi) {ret=0}} END{exit ret}' \
    /proc/fs/nfsfs/volumes", \
  ATTR{read_ahead_kb}="15360"
----

See link:eda-afx-performance.html#nfs-read-ahead[Performance — NFS read-ahead] for the full read-ahead configuration script and distribution-by-distribution default values.

TIP: Verify read-ahead values after OS upgrades. Upgrading from RHEL 7.x to RHEL 8.3+ drops read-ahead from 15,360 KiB to 128 KiB silently. Add read-ahead verification to post-upgrade checklists.

=== Kernel-level NFS concurrency tuning

==== NFSv3: sunrpc slot table

----
# Add to /etc/sysctl.conf
# Limit per-connection concurrency to 128; default (65,536) is excessive for large EDA farms
echo "sunrpc.tcp_max_slot_table_entries=128" >> /etc/sysctl.conf
sysctl -p
# Remount NFS filesystems to apply
----

For large EDA farms (100+ clients per storage endpoint), reduce this further to keep total environment-wide slot count below 10,000. See link:eda-afx-performance.html#nfs-concurrency-and-slot-table-tuning[Performance — NFS concurrency] for per-client sizing guidance.

==== NFSv4.1: max_session_slots

----
# Set NFSv4.1 session concurrency to match server maximum (180)
echo "options nfs max_session_slots=180" > /etc/modprobe.d/nfsclient.conf
reboot
----

With `max_session_slots=180` and `nconnect=8`, each NFSv4.1 session supports 180 outstanding requests distributed across 8 connections — well above the 128-per-connection limit that would cap a single-connection session at 128.

=== Linux filesystem cache tuning

For EDA compute nodes running write-heavy simulation jobs, add the following to `/etc/sysctl.conf`:

----
# Cap dirty buffer accumulation to prevent write-burst NFS latency spikes
vm.dirty_bytes=31457280
vm.dirty_background_bytes=6291456
# Flush dirty buffers after 3 seconds (default is 30; too long for write-dominant scratch jobs)
vm.dirty_expire_centisecs=300
# Wake the flush thread every second (default is 5; aligns with 3-second expire)
vm.dirty_writeback_centisecs=100
----

Apply immediately:

----
sysctl -p
----

These settings prevent the write-behind cache from accumulating excessive dirty data on nodes with large amounts of RAM (256 GiB+), which causes the NFS write latency symptoms described in link:eda-afx-performance.html#linux-filesystem-cache-tuning[Performance — Linux filesystem cache tuning].

*Recommended mount options by volume type*

| PDKs / Cell libraries | `vers=4.2,nconnect=8,rsize=1048576,wsize=1048576,nocto,actimeo=600,ro,trunkdiscovery`
| Performance scratch (read/write) | `vers=4.2,nconnect=8,rsize=1048576,wsize=1048576,tcp,timeo=600,retrans=2,trunkdiscovery`
| Project workspaces (FlexClone) | `vers=4.2,nconnect=8,rsize=1048576,wsize=1048576,tcp,timeo=600,retrans=2,trunkdiscovery`
| Home directories (Tier 2, Kerberos) | `vers=4.2,sec=krb5p,rsize=262144,wsize=262144,tcp`
|===

NOTE: Home directory mounts on Tier 2 systems use 256 KiB rsize/wsize and Kerberos. Kerberos is incompatible with `nconnect`; omit `nconnect` on any mount using `sec=krb5*`.

== Security

* *Enable ARP on all volumes* containing proprietary design data. Tools, libraries, scratch, workspaces, and project archives all represent valuable IP that ransomware can target.

* *Use NFS Kerberos* for authentication on sensitive design namespaces. Avoid AUTH_SYS (Unix UID/GID) for volumes containing PDKs, cell libraries, or tape-out data, where the risk of unauthorized access is highest.

.Zero Trust security architecture for EDA storage: identity-verified NFS, micro-segmented export policies, encrypted data paths
image::zero-trust-architecture.png[Zero Trust architecture for EDA storage protecting chip design IP,align="center"]

* *Apply export policy rules that restrict each volume* to the specific subnets or host IP ranges that require access. A PDK volume should not be accessible from the corporate LAN; it should only be exportable to the HPC cluster's storage VLAN.

.Attribute-Based Access Control architecture for fine-grained access policy enforcement across EDA volumes
image::abac-access-architecture.png[ABAC architecture for EDA storage access control by role project and sensitivity,align="center"]

* *Enable NVE (NetApp Volume Encryption)* with an external key manager (OKM or external KMIP-compatible KMS) for all volumes containing proprietary design data. This ensures that physical drive theft does not result in a data breach.

.Two-layer encryption model: NVE at the volume level and NAE at the storage layer for EDA data protection
image::zero-trust-two-layer-encryption-solution-aff-fas.png[NVE and NAE two-layer encryption for EDA data at rest,align="center"]

* *Take a Snapshot immediately before any infrastructure change* that could affect running EDA jobs. This provides a rollback point if a tool update, export policy change, or volume configuration modification has unintended consequences.

* *Configure SNMP traps or Harvest/Grafana alerts* for ARP events, volume capacity thresholds (>80% full), and NFS latency exceedances. Route these alerts to the storage operations team and, for ARP events, to the security operations center.

* *Audit NFS access logs* periodically to identify unusual access patterns, such as an individual account accessing large quantities of library or PDK data outside normal working hours.

== Data lifecycle

* *Define tiering policies by dataset category at volume creation time.* Retroactive tiering scans add I/O load to production volumes and should be avoided during active design phases.

* *Cold data from AFX must go to Tier 2 via SnapMirror first.* Configure SnapMirror relationships from AFX to Tier 2 AFF C-Series or FAS at project milestones. FabricPool on Tier 2 handles the cold-to-object transition. Never configure FabricPool tiering on AFX volumes directly — it is not supported.

* *Configure SnapMirror to replicate active AFX design data to a secondary site* on a daily or hourly schedule. This provides both disaster recovery and the cold data migration path.

* *Retain tapeout Snapshots for at least three years* to support re-spin analysis, manufacturing process validation, and regulatory compliance. Store these on SnapMirror destinations and verify their integrity annually.

* *Use FlexClone for engineer workspaces, not full copies.* Enforce a maximum workspace lifetime policy (typically 30–60 days) to prevent clone sprawl. Automate workspace creation and deletion through a portal or HPC job scheduler integration.

* *For AI training data retention,* identify which simulation result datasets are candidates for ML model training before archiving. Replicate high-value training data to a designated S3 bucket or object store before cold tiering removes it from accessible storage.

== HPC scheduler integration

* *Configure separate queues for Tier 1 and Tier 2 storage workloads* in the HPC job scheduler (LSF, Slurm, PBS, or Grid Engine). This prevents low-priority background jobs from consuming AFX bandwidth during peak tapeout simulation runs where Tier 1 performance directly gates license utilization.

* *Specify NFS mount dependencies in job submission scripts.* Jobs that require Tier 1 AFX mounts should fail fast (with a clear error) rather than hanging if the mount is unavailable. A job that hangs waiting for a mount consumes a license slot without doing useful work.

* *Monitor per-queue storage I/O consumption* to identify which job types are the heaviest consumers of AFX bandwidth. This data informs both scheduler tuning (setting per-queue bandwidth limits) and capacity planning (identifying when additional nodes or shelves are needed).

* *Configure health check commands* in the job scheduler that validate NFS mount responsiveness before dispatching jobs to compute nodes. A compute node with a degraded NFS mount should be excluded from scheduling until the mount is healthy.

* *For FlexClone workspace lifecycle management,* integrate clone creation and deletion with the scheduler's job lifecycle hooks. Create a workspace when a project job set is submitted; schedule workspace cleanup when the job set completes and results are committed to source control.

== Monitoring and observability

* *Deploy Grafana Harvest version 25.11.0 or later* for AFX cluster monitoring. Harvest provides pre-built dashboards for NFS throughput, latency, volume utilization, and cluster health metrics that cover AFX-specific counters.

* *Create per-volume latency alerts* that trigger when read or write latency on Tier 1 AFX volumes exceeds 1ms during business hours. Sustained latency above 1ms during active simulation indicates a potential bottleneck that affects job throughput.

* *Monitor FlexGroup constituent imbalance* using ONTAP CLI or Harvest. Advanced Capacity Balancing prevents large-file imbalance in AFX, but access pattern skew can still develop. Alert when constituent used-percentage variance exceeds 20%.

* *Use ONTAP REST API for automation and capacity reporting.* Build a daily capacity forecast that projects days-to-full for each AFX volume based on the rolling 7-day average growth rate. Route projections above 80% capacity to the storage team with at least 30 days advance notice.

* *Monitor backend switch utilization* on the 400GbE Cisco Nexus fabric. NVRAM replication traffic on the backend network increases with write I/O load. Track backend switch port utilization alongside AFX write workload to validate that the backend fabric has adequate headroom.

NOTE: NetApp ActiveIQ Unified Manager is not supported on AFX. Use Grafana Harvest as the primary monitoring and alerting platform. ONTAP System Manager and the ONTAP REST API are also available for cluster management and integration with external monitoring systems.
