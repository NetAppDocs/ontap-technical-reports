= Storage design
:icons: font
:imagesdir: ./media

[.lead]
EDA storage architectures require a tiered approach that aligns storage resource characteristics to workload requirements. Different datasets have fundamentally different performance profiles, access patterns, and retention requirements. A well-designed tiered architecture delivers extreme performance where it matters, controlled cost where it does not, and correct cold-data lifecycle management throughout.

== Tiered design

=== Tier 1 — Extreme performance (AFX)

Tier 1 handles the datasets that directly gate EDA job throughput. Every running simulation job reads from this tier simultaneously, so metadata rate, sequential bandwidth, and read latency on this tier have a multiplying effect on the entire HPC cluster's throughput.

Datasets for Tier 1 (AFX):

* EDA tool installations
* Process design kits (PDKs) and cell libraries
* Performance scratch volumes for active simulation jobs
* FlexClone workspaces for active design projects
* IP blocks and reference designs actively in use

AFX FlexGroup volumes distribute the metadata workload across all nodes in the cluster, eliminating the single-namespace hotspots that appear when hundreds of EDA jobs simultaneously open and read library files. Global deduplication (ONTAP 9.19.1+) ensures that tool trees replicated across multiple SVMs for team isolation consume minimal on-disk space.

=== Tier 2 — Balanced performance (AFF A-Series or AFF C-Series)

Tier 2 handles important datasets that are less latency-sensitive than active simulation scratch but still require good NFS performance. This tier also serves as the intermediate layer for cold data lifecycle management.

Datasets for Tier 2 (AFF A-Series or C-Series):

* HPC job scheduler data (LSF, Slurm, PBS)
* Source control repositories (Perforce, Git)
* Build artifacts and regression results
* Emulation platform storage
* Home directories
* Completed project archives awaiting cold tiering

*Cold data tiering from Tier 2:* AFF C-Series and FAS systems support FabricPool. Cold data that has been SnapMirrored from Tier 1 to Tier 2, or that originated on Tier 2, can be automatically tiered to object storage (S3, Azure Blob, or Google Cloud Storage) using FabricPool's temperature-based tiering policies.

IMPORTANT: FabricPool is not supported on AFX. Cold data archival from AFX-hosted volumes requires SnapMirror replication to a Tier 2 AFF C-Series or FAS system. That Tier 2 system can then tier cold data to object storage using FabricPool. Do not attempt to configure FabricPool tiering policies on AFX-hosted volumes.

=== Tier 3 — Cold archive (object storage via Tier 2 FabricPool)

Completed project data, old tapeout archives, and results that must be retained for compliance or re-spin analysis but are rarely accessed can be tiered to object storage through FabricPool on a Tier 2 system. ONTAP monitors access temperature per block and moves cold blocks to the capacity tier without administrator intervention.

Cold data workflow from AFX:

. Active project data lives on Tier 1 (AFX) during active design and simulation.
. At project completion or milestone, SnapMirror replicates the dataset from Tier 1 AFX to Tier 2 AFF C-Series.
. The Tier 2 volume is placed under a FabricPool tiering policy with an appropriate cooling period (typically 7–31 days depending on re-access likelihood).
. Cold blocks migrate from Tier 2 NVMe to object storage automatically.
. For long-term archive, SnapMirror Cloud from Tier 2 can stage the entire dataset directly to cloud object storage.

=== Topology notes

* AFX serves Tier 1 data over NFSv4.2 (recommended) or NFSv3 directly to HPC compute nodes.
* Tier 2 AFF C-Series handles balanced workloads and serves as the FabricPool-capable landing zone for cold data from AFX.
* Object storage (on-premises S3 or cloud) is attached only to Tier 2, not directly to AFX.
* SnapMirror relationships from AFX to Tier 2 run on a scheduled basis (typically nightly or at project milestones) for cold data promotion.
* A dedicated SnapMirror relationship should also exist from AFX to Tier 2 (and optionally cloud) for disaster recovery purposes, separate from the cold data pipeline.

== Networking design

EDA jobs are highly parallel. A single verification run can launch hundreds of jobs simultaneously, all reading library files from the same NFS mount points. Without proper network load balancing, individual data LIFs can become throughput bottlenecks even when the aggregate cluster bandwidth is sufficient.

=== LIF placement

Configure at least one data LIF per node per data network for AFX clusters serving EDA workloads. This ensures that no single LIF becomes the choke point for large simulation jobs, and allows the NFS client load to distribute across all nodes.

For a 16-node AFX cluster with two data networks, configure a minimum of 32 data LIFs (16 per network). DNS round-robin or an external load balancer (such as F5) should distribute NFS client mount connections across all LIFs so that no individual LIF handles a disproportionate share of the client load.

=== Front-end network

* *Link speed:* 100GbE per node minimum for Tier 1 AFX. This matches the node's throughput capability and avoids front-end saturation during concurrent simulation jobs.
* *Jumbo frames:* Enable 9000 MTU end-to-end if the network fabric supports it. Jumbo frames reduce per-packet CPU overhead for large sequential transfers, which benefits library reads and scratch writes.
* *BGP ECMP or DNS round-robin:* Use equal-cost multipath routing or DNS round-robin to distribute NFS sessions across all LIFs. This is especially important for tool and library volumes that are read simultaneously by hundreds of HPC nodes.

=== NFS client tuning

For hosts running EDA tools, apply the following client-side NFS mount tuning:

----
vers=4.2,nconnect=16,rsize=1048576,wsize=1048576,nocto,tcp,timeo=600,retrans=2,trunkdiscovery
----

Parameter guidance:

*NFS mount parameter guidance*

[options="header"]
|===
| Mount parameter | Guidance
| `vers=4.2` | Use NFSv4.2 for new EDA deployments. NFSv4.1 and 4.2 provide substantial performance improvements over NFSv3 for sequential reads and, with ONTAP 9.18.1, are now competitive with NFSv3 for metadata operations. See link:eda-afx-performance.html[Performance].
| `nconnect=16` | Allow 16 parallel TCP connections per mount point. This is critical for saturating the available bandwidth from AFX on NFS-capable hosts. Values up to 16 are supported on modern Linux kernels.
| `rsize=1048576,wsize=1048576` | Set 1MB read and write block sizes for sequential I/O. This maximizes transfer efficiency for library reads and scratch writes.
| `nocto` | Disable close-to-open consistency on read-only library and tool mounts. Eliminates unnecessary server round-trips on file open/close for data that does not change.
| `trunkdiscovery` | Enable NFSv4.1/4.2 session trunking (pNFS path discovery). Allows a single NFS mount to use multiple paths and spread load across all available LIFs automatically.
| TCP slot tables | Configure kernel TCP slot tables to at least 128 per session (`sunrpc.tcp_slot_table_entries=128`) to avoid NFS request queue saturation under heavy parallel workloads.
|===

TIP: For library and tool volumes that are truly read-only (PDKs, EDA tool installations), mount with the `ro` flag in addition to `nocto` to enforce read-only access at the OS level and prevent accidental writes that could corrupt the baseline.

=== Backend network

The AFX backend network carries both data traffic (node-to-shelf) and NVRAM replication traffic (HA pair heartbeat and write acknowledgment). The backend uses:

* 400GbE Cisco Nexus switches
* 4x100GbE breakout cables per node to the backend switches
* NSM140 shelves with 16x100GbE RoCE Ethernet ports per shelf

The NVRAM replication traffic added in AFX (vs. the direct NVRAM interconnect in unified ONTAP) adds a relatively small but non-zero load to the backend fabric. For large clusters approaching maximum shelf counts, validate that backend switch port capacity and switch fabric bandwidth are sufficient for the combined data and NVRAM replication load.

=== Storage network segmentation

Isolate EDA storage networks from general-purpose corporate networks. At a minimum:

* Separate VLANs for AFX data traffic, AFX management traffic, and AFX replication (SnapMirror) traffic.
* Dedicated physical switches or a dedicated leaf-spine tier for high-throughput storage traffic, separate from the office network.
* QoS policies to protect storage traffic from interference during peak simulation runs, if the fabric is shared with other services.
