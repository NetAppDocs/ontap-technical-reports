= How to remove AFX nodes
:icons: font
:imagesdir: ../media/afx/

[.lead]
This page describes how to remove storage nodes from a NetApp AFX cluster. Because AFX uses a shared Storage Availability Zone and link:afx-architecture-volume-moves.html#zero-copy-volume-moves[zero-copy volume moves], node removal differs from unified ONTAP: volumes leave a node without a data copy, and HA partners must be removed as a pair. For architectural background, see link:afx-architecture-cluster-scale.html#node-additions-and-removals[Node additions and removals].

== What is different in NetApp AFX

* Multiple HA pairs can share one Storage Availability Zone (SAZ). After you remove a pair, other nodes stay in the cluster.
* Volumes can leave the node with zero-copy volume move (ZCVM) (no data copy).
* Unjoin is `cluster remove-node`. After one node is gone, the only node you may remove next is its HA partner.

== Prerequisites (check before you start)

Run unjoin from a different, healthy node (not the node you are removing). Prefer advanced privilege.

Confirm:

. Cluster and rings are healthy (`cluster show`, `cluster ring show`).
. The node is online/healthy.
. Node is not epsilon (or you will move epsilon after evacuation).
. No data LIFs remain homed/current on that node (except cluster LIFs/node-mgmt, which go away with the node).
. Volumes that cannot ZCVM are handled first (clones, offline volumes, NVE rekey, SnapMirror-to-cloud / SMC restore, audit MDV).

== Step-by-step: remove one node (node is up)

Replace `<NODE>` with the node to remove, `<OTHER>` with a surviving node.

=== Evacuate volumes (required)

----
system node evacuate-volumes start -node <NODE>
system node evacuate-volumes show -node <NODE>
----

Wait until pending count is 0. Do not move epsilon or eligibility until this finishes.

If `remove-node` later says the node still has volumes, re-run evacuate (or resolve ZCVM blockers). Audit staging / root volumes are handled by unjoin, not by you.

Optional abort:

----
system node evacuate-volumes abort -node <NODE>
----

=== Migrate data LIFs off the node

----
network interface show -curr-node <NODE>
network interface migrate -vserver <SVM> -lif <LIF> -dest-node <OTHER> -dest-port <PORT>
----

Repeat until only cluster LIFs and node-mgmt remain on `<NODE>`.

=== Move cluster epsilon (only if it is on `<NODE>`)

Do this after evacuate completes.

----
cluster show -epsilon true
cluster modify -node <OTHER> -epsilon true
----

=== If `<NODE>` is an RDB ring master, make it ineligible

Do this after evacuate completes.

----
cluster ring show
cluster modify -node <NODE> -eligibility false
----

=== Change home-node of remaining data LIFs

----
network interface show -home-node <NODE>
network interface modify -vserver <SVM> -lif <LIF> -home-node <OTHER>
----

Leave cluster LIFs and node-mgmt LIFs on the departing node.

=== Disable takeover of that node

----
storage failover modify -node <NODE> -enable-takeover-of false
storage failover show
----

Expect takeover not possible on that pair while failover is disabled.

=== Unjoin

----
cluster remove-node -node <NODE>
----

Alias: `remove-node` in advanced privilege.

Confirm the warnings. The job should end with `Node remove succeeded`.

Unjoin does the following:

* Marks the node ineligible / out of CLAM quorum
* Cleanly shuts the node down (fails if shutdown is not clean)
* Cleans RAID/HA per-node state and deletes the site from the cluster DB

=== Remove the HA partner next

After one node is removed, only its partner may be removed until that pair is gone.

Repeat the previous steps for the partner. Then you can remove a different pair.

=== Clean the removed hardware (optional)

From each removed node's boot menu: option 4 — Clean configuration and initialize all disks.

To reuse the pair in the same cluster: `cluster add-node` after both nodes of the pair are removed and reinitialized.
