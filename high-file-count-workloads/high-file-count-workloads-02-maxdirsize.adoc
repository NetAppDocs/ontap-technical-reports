= Maxdirsize and large ONTAP directories
:icons: font
:imagesdir: ../media/high-file-count-workloads/

[.lead]
`maxdirsize` limits the size of each directory file in an ONTAP volume by capping the capacity that can be allocated for the names in that directory. It is independent of the volume's `maxfiles` inode limit, and there is no static definable limit for number of names in a single directory because that value is variable and based on a number of factors, such as name length, character types, etc. For details, see link:high-file-count-workloads-02-maxdirsize.html#estimating-the-number-of-names-per-directory-file[Estimating the number of names per directory file].

== What is a directory in ONTAP?

A WAFL directory is a metadata file that maps names to inode numbers. Its size is not the sum of the data stored in the files below that directory, but instead is a factor of how many names the directory holds and how much directory space each of those names needs. A newly created directory starts at 4 KiB and grows in 4 KiB directory blocks as entries are added.

The directory consumes one inode, whose record is stored in the volume-level inode file (which is separate in concept and function). The directory's names are stored in that directory's own data blocks. Adding more names grows the individual directory file and can approach the `maxdirsize` limit, while creating more file-system objects (such as files, directories, ACLs, and named streams) allocates more inode records and can grow the volume-level inode file toward `maxfiles` limits. The number of name entries in a single 4KiB directory block is determined by how each name has to be stored, which depends on its length and character encoding.

=== Directory-block layout

An ONTAP directory file grows in 4 KiB blocks, where each block is limited to a variable number of entry records and name chunks based on the size of each. A name chunk in ONTAP is a 16-byte slot that stores part of a filename; each name occupies one entry record plus as many 16-byte chunks as its encoded length requires.

Example of how name chunks would be allocated across a 48 byte name:

=== Max number of directory blocks and maximum number of names

The maximum number of directory blocks allowed is determined by the maxdirsize value. 

With a 320MB directory size, up to 81,920 directory blocks can be allocated (320MB/4KiB, where 320MB is 335,544,320 bytes because ONTAP reports these values in binary units). As such, the total number of names allowed in the directory file depends on the number of entries allowed per directory block.

Every 4 KiB directory block is divided the same way:

* Up to 128 entry records of 12 bytes each (1536 bytes)
* A shared pool of 160 name chunks of 16 bytes each (2560 bytes)

Together these occupy one 4 KiB block. Each stored name needs an entry record and one or more name chunks, and whichever pool runs out first — the 128 entry records or the 160 name chunks — sets how many names that block can hold. With ASCII names, the name chunks are what run out first. As a result, neither `maxdirsize / filename-length` nor a fixed files-per-megabyte ratio is exact.

=== Estimating the number of names per directory file

To roughly estimate how many names fit in one directory, work at the level of the 4 KiB directory block and then multiply by the number of blocks the cap allows:

----
names in one directory = names per block × number of 4 KiB blocks
----

At a 320MB cap that block count is 81,920 (335,544,320 / 4096). The names per block is set by how many of the block's 160 name chunks each entry consumes, rounding each division up:

* Standard ASCII names: `chunks = max(3, (name length / 16) + 1)`. The floor of 3 chunks means any name up to 32 characters costs the same 3 chunks, so a block always holds 53 of them (160 / 3), whether the name is 3 characters or 32.
* Long-form names, which ONTAP uses whenever the name contains non-ASCII characters, stores an NFS alternate name, or represents a FlexGroup remote entry: `chunks = max(3, (name length × 2 / 16) + 2)`, because those names are counted at UTF-16 width. An NFS alternate name adds eight characters to the name length first.
* An SMB DOS 8.3 alias stored alongside the long name adds approximately three more chunks.

`names per block = 160 / chunks`, capped at the block's 128 entry records. For normal names the 3-chunk floor keeps this at 53 or fewer, so the 128-record cap is only reached by legacy DOS 8.3 names that fit in a single chunk. Longer or long-form names use more chunks and therefore pack fewer per block, which is why the total varies.

=== Why the number of names varies

The following factors change how much directory-file space each entry consumes:

* Filename length
* ASCII compared with non-ASCII characters
* Unicode long-form representation
* An additional NFS alternate name, when required
* An SMB DOS 8.3 alias, when generated
* FlexGroup remote-entry representation
* Deleted-entry fragmentation and how well new names reuse available slots

This is why there is no absolute number of files allowed in a single directory. Public guidance commonly cites approximately 4.3 million names at a 320 MiB setting for a FlexVol volume. That number works out to roughly 78 *bytes* of directory file per name (4 KiB divided by the 53 short ASCII names that fit in a block) and applies to any standard ASCII name up to 32 characters; it does not mean the average filename is 78 characters long. Since file names are highly variable, those numbers can shift one way or the other. === Filename length compared with path length

`maxdirsize` accounts for the basename stored in a particular parent directory. It does not store the entire absolute path with every entry. Each pathname component is an entry in its own parent directory.

A deeper hierarchy adds directories and public inodes, but it reduces the number of names stored in each directory. This tradeoff usually improves scalability. Protocol and client path-length limits still apply independently.

== What maxdirsize actually measures

The volume `maxdir-size` value is the maximum directory-file size allowed for every individual directory in that volume. For instance, a setting of 320 MB means that no directory file in the volume can grow beyond 320 MB. The setting does not reserve 320 MB of volume capacity; it simply grows into that value. A newly created directory starts at 4 KiB, but if that directory file later grows to 320 MB of directory-file blocks, it uses 320 MB of actual volume capacity for those blocks. Once that directory file grows, the directory-file size remains at that high-water mark even if directory entries are removed. Deletion of files or directories makes those entry slots reusable, but it does not compact the directory. Indexed directories can hole-punch fully empty 4 KiB blocks (available in ONTAP 9.5 and later) and reclaim those physical blocks, but the reported directory-file size does not normally shrink.

The companion directory index that ONTAP creates for large directories consumes its own metadata capacity and an inode, but it is not part of the directory file and does not count against `maxdirsize`. See link:high-file-count-workloads-04-maxdirsize-indexing.html[Directory indexing in ONTAP].

=== Raising the maxdirsize value

* Applies to all directories in the volume
* Allows directory files to grow beyond the former cap
* Does not preallocate or reserve the new maximum
* Does not add public inodes or change `maxfiles`
* Does not make an existing directory consume space immediately

For how to inspect the configured cap and a directory's current size, see link:high-file-count-workloads-03-maxdirsize-view.html[View maxdirsize and current directory size].
