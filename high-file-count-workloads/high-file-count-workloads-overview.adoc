= NetApp ONTAP High File Count Workloads for NAS volumes
:icons: font
:imagesdir: ../media/high-file-count-workloads/

[.lead]
High-file-count NAS workloads place more emphasis on namespace and metadata operations than workloads dominated by a smaller number of large files. This document set explains how NetApp ONTAP stores and manages large file populations, how to distinguish the `maxfiles` and `maxdirsize` limits, and how to plan NAS namespaces for predictable capacity and performance.

== What is meant by a high-file-count workload?

There is no single file-count threshold at which every workload becomes a high-file-count workload. The effect depends on more than the total number of files:

* How many files and directories exist in a volume
* How many entries are concentrated in each directory
* The rate at which files are created, opened, enumerated, renamed, and deleted
* Filename length, character set, and protocol-generated alternate names
* Whether access is spread across directories, FlexGroup constituents, and cluster nodes
* How often applications scan or list the entire namespace
* The number and retention of Snapshot copies

A workload should be treated as high file count when its projected namespace can materially affect inode planning, directory-file growth, metadata capacity, client-operation latency, backup or replication behavior, or recovery time. A workload with several million files distributed across many directories can behave differently from one that places the same number of files in a single directory.

== Workloads commonly associated with high file counts

Examples include:

* Electronic design automation (EDA) and semiconductor design flows
* Software source trees, package repositories, and continuous integration build areas
* Artificial intelligence and machine learning datasets containing images, tokens, checkpoints, or other small objects
* Genomics and life-sciences pipelines
* Media rendering, visual-effects, and animation frame repositories
* Home directories, departmental shares, and content-management repositories
* Analytics, telemetry, and logging environments that create many short-lived files
* Scientific and high-performance computing scratch spaces

File size alone does not identify these workloads. A dataset can have modest capacity while consuming many inodes, and it can have enough total inodes while still exceeding the size allowed for one directory.

== High-file-count challenges

=== Metadata operations

Each file or directory requires an inode and namespace metadata. File creation, lookup, attribute retrieval, rename, enumeration, and deletion can therefore dominate the workload even when data throughput is low. Protocol behavior also matters: NFS and SMB clients can issue different combinations of lookup, open, close, attribute, and directory-read operations.

=== Capacity

ONTAP stores public inodes in a hidden, volume-level inode file. Each ONTAP 9 inode uses 288 bytes. The inode file and each directory file consume capacity independently:

* The *inode file* holds inode records for the FlexVol or FlexGroup constituent. `maxfiles` (`files`) is an inode count, not a byte cap. Raising it does not reserve space. The file grows as ONTAP allocates more inode records, using about `inode count × 288` bytes of actual capacity. One million allocated public inodes use about 288 MB. Deleting files frees inodes for reuse but does not shrink the inode file.
* A *directory file* stores one directory's names and mappings to inode numbers. `maxdirsize` limits each directory independently. A 320 MB setting is a cap, not a reservation; the directory file grows into that value. A new directory starts at 4 KiB. If it later grows to 320 MB of directory-file blocks, those blocks use 320 MB of actual volume capacity. After growth, the directory-file size remains at that high-water mark even if entries are removed; deletion makes slots reusable but does not compact the directory. Indexed directories can hole-punch fully empty 4 KiB blocks (available in ONTAP 9.5 and later) and reclaim those physical blocks, but the reported size does not normally shrink. Companion indexes consume additional capacity.

A volume can use hundreds of megabytes in the inode file with every directory far below `maxdirsize`, or 320 MB in one directory file with a still-small inode file.

=== Directory enumeration

Large directories take longer to enumerate than smaller ones. A sparse directory that remains at its high-water size can still be expensive to scan, even when hole punching lets `READDIR` skip empty blocks. Avoid unnecessary full-directory scans.

=== Failure-domain concentration

Concentrating millions of entries in one directory creates a single-directory scaling and serialization point. Distributing files across a hierarchy means using more directories with fewer files in each directory. That layout generally improves parallelism, reduces the scope of directory scans, and makes operational tasks easier.

=== Data protection and recovery

High object counts can extend namespace scans, backup cataloging, replication, restore processing, and post-restore directory-index construction. SnapMirror replicates changed metadata as well as file data, so a baseline or update with many creates, deletes, or renames can be expensive even when the files are small. Measure those operations with a representative object count.

For directory-index transfer with SnapMirror, see link:high-file-count-workloads-maxdirsize.html[Maxdirsize and large ONTAP directories].

== Maxfiles compared with maxdirsize

`maxfiles` and `maxdirsize` protect different resources. Neither is a substitute for the other.

[options="header"]
|===
| Attribute | Scope | Measures | Typical symptom at the limit

| `maxfiles`
| A FlexVol volume, or a FlexGroup as a whole with the configured total distributed across its constituents
| Public inodes available for files, directories, streams, ACLs, and other user-visible file-system objects
| New objects cannot be created because no public inode is available. NFS clients typically receive `ENOSPC`. SMB clients typically receive `STATUS_DISK_FULL`.

| `maxdirsize`
| Each individual directory
| Maximum size of the WAFL directory file, not a fixed number of names
| New names cannot be added to that directory even if the volume has free inodes and capacity. NFS clients typically receive `ENOSPC`. SMB clients typically receive `STATUS_DISK_FULL` or `STATUS_CANNOT_MAKE`.
|===

A volume can have ample free inodes and still reach `maxdirsize` in one directory, or avoid large directories and still exhaust the public inode supply.

== What is maxdirsize?

`maxdirsize` is the per-volume cap on how large any single WAFL directory file can grow. It is a capacity value, not a fixed number of names. Filename length, Unicode representation, SMB 8.3 aliases, NFS alternate names, and FlexGroup remote-entry representation all change directory size behavior. Increasing the setting authorizes growth; it does not preallocate space.

For calculation details, directory indexing, capacity and performance effects, volume-type considerations, release enhancements, and EMS events, see link:high-file-count-workloads-maxdirsize.html[Maxdirsize and large ONTAP directories].

== What is maxfiles?

`maxfiles` is the configured ceiling for public inodes: files, directories, streams, ACLs, and other user-visible objects. It is an inode count, not a directory byte size, and it is not the same as current inode-file allocation. ONTAP grows the inode file when an operation needs another public inode and no free record remains, up to `files` and available capacity. That includes creating a file or directory, allocating an extra inode for a stream or ACL, and creating a public directory-index inode after directory-index transfer is enabled. The configurable maximum depends on volume size and ONTAP limits.

For inode accounting, capacity, controls, release behavior, limits, and EMS events, see link:high-file-count-workloads-maxfiles.html[Maxfiles and ONTAP inode limits].

== Planning approach

Begin with four separate estimates:

. Total file-system objects over the workload lifecycle
. Peak entries in the largest directory
. Peak create, lookup, enumeration, and delete rates
. Capacity for user data, inodes, directories, directory indexes, Snapshot copies, and growth

Use the following methods to gather those inputs:

=== Find total objects and inode headroom

Compare application inventory with ONTAP's public-inode counters:

----
volume show -vserver <svm> -volume <volume> -fields files,files-used

set -privilege advanced
volume show -vserver <svm> -volume <volume> -fields files-maximum-possible,inodefile-public-capacity
----

For FlexGroup, inspect both the configured total and every constituent's use:

----
volume show -vserver <svm> -volume-style-extended flexgroup-constituent -fields files,files-used
----

Include projected files, directories, streams, ACLs, public directory indexes, temporary objects, and migration overlap. Use the application's inventory or migration assessment to forecast future growth; `files-used` describes the current namespace, not the future peak.

=== Find the largest directories

Use application inventory, migration tools, or a controlled namespace scan to identify directories with the most entries. Review `wafl.dir.size.warning` and related EMS events for directories already approaching the limit. On a GNU/Linux NFS client, inspect the directory object itself:

----
stat -c '%n %s bytes' /mount/path/directory
----

Do not substitute `du`; it reports the data below the directory rather than the directory metadata-file size. Model filename lengths and alternate names as described in link:high-file-count-workloads-maxdirsize.html[Maxdirsize and large ONTAP directories].

=== Measure metadata operation rates

Use application telemetry, client workload tools, packet traces, ONTAP performance statistics, or a monitoring tool such as Harvest to measure create, lookup, open, close, attribute, enumeration, rename, and delete rates. Test representative concurrency and both warm- and cold-cache behavior. A bandwidth-only test does not characterize a metadata-heavy workload.

=== Find metadata and Snapshot capacity

Use `volume show-space` to separate user data, file-system metadata, inodes, and Snapshot reserve. Use `volume show-footprint` to review the volume's aggregate footprint. Estimate raw ONTAP 9 inode records as `peak allocated inodes × 288 bytes`, then add directory files, companion indexes, block rounding, private metadata, Snapshot-retained blocks, and growth margin.

Do not derive `maxdirsize` directly from the total volume file count, and do not use `maxfiles` to estimate how many names fit in one directory.

For design and operational recommendations, see link:high-file-count-workloads-best-practices.html[High-file-count NAS workload best practices].
