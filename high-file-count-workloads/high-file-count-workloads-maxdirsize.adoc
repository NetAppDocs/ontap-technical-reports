= Maxdirsize and large ONTAP directories
:icons: font
:imagesdir: ../media/high-file-count-workloads/

[.lead]
`maxdirsize` limits the size of each directory file in an ONTAP volume. It does not directly specify a maximum number of names, and it is independent of the volume's `maxfiles` inode limit. This page explains directory-file packing, indexing, measurement, operational effects, release enhancements, and relevant EMS events.

== What maxdirsize measures

A WAFL directory is a metadata file that maps names to inode numbers. Its size is not the sum of the data stored in the files below that directory. A newly created directory starts at 4 KiB and grows in 4 KiB directory blocks as entries are added.

The directory file is not the volume's inode file. The directory itself consumes one inode, whose record is stored in the volume-level inode file. The directory's names are stored in that directory's own data blocks. Adding more names grows the individual directory file and can approach `maxdirsize`; creating more file-system objects allocates more inode records and can grow the volume-level inode file toward `maxfiles`.

The volume `maxdir-size` value is the maximum directory-file size allowed for every individual directory in that volume. Raising the value:

* Applies to all directories in the volume
* Allows directory files to grow beyond the former cap
* Does not preallocate or reserve the new maximum
* Does not add public inodes or change `maxfiles`
* Does not make an existing directory consume space immediately

Directory files are high-water structures. Deleting names makes slots reusable, but the reported directory-file size does not normally shrink.

== How maxdirsize is calculated in ONTAP

=== Directory-block layout

An ONTAP directory file grows in 4 KiB blocks. The following implementation-level packing model is useful for estimation but is not a guaranteed public on-disk interface. In this model, each block contains:

* 128 entry records of 12 bytes each
* 160 name chunks of 16 bytes each

Together these occupy one 4 KiB block. Each stored name needs an entry record and one or more name chunks. As a result, neither `maxdirsize / filename-length` nor a fixed files-per-megabyte ratio is exact.

A planning model is:

----
estimated directory-file bytes =
    directory entry count × average on-disk bytes per entry
----

Round the result up to 4 KiB blocks and leave operating margin. The average on-disk entry footprint must account for filename representation, not only the visible character count.

=== Why the number of names varies

The following factors change how much directory-file space each entry consumes:

* Filename length
* ASCII compared with non-ASCII characters
* Unicode long-form representation
* An additional NFS alternate name, when required
* An SMB DOS 8.3 alias, when generated
* FlexGroup remote-entry representation
* Deleted-entry fragmentation and how well new names reuse available slots

Public guidance commonly cites approximately 4.3 million names at a 320 MiB setting when the average filename is 78 characters. That is an example, not a guarantee. Measure or model the application's actual names before selecting a cap.

=== Filename length compared with path length

`maxdirsize` accounts for the basename stored in a particular parent directory. It does not store the entire absolute path with every entry. Each pathname component is an entry in its own parent directory.

A deeper hierarchy adds directories and public inodes, but it reduces the number of names stored in each directory. This tradeoff usually improves scalability. Protocol and client path-length limits still apply independently.

== View maxdirsize and current directory size

=== View the configured cap

----
set -privilege advanced
volume show -vserver <svm> -volume <volume> -fields maxdir-size
----

This reports the per-directory cap, not the size of a particular directory.

=== View the directory file from an NFS client

On a mounted NFS path from a GNU/Linux client, use `stat` or a long directory listing on the directory object itself:

----
stat -c '%n %s bytes' /mount/path/directory
ls -ld /mount/path/directory
----

Do not use `du` for this purpose. `du` reports data reachable below the directory, whereas `maxdirsize` applies to the directory metadata file itself.

Client tools and protocols do not all report directory-file size consistently. An NFS client is the preferred client-side method when exact directory-object size is required.

=== Locate a directory reported by EMS

The maxdirsize EMS event includes a volume and file ID. Resolve that inode to a path with:

----
volume file show-inode -vserver <svm> -volume <volume-or-constituent> -inode-number <file-id>
----

The reported file ID belongs to the directory that reached or approached the limit, not to the file whose creation failed. For a FlexGroup, `volume file show-inode` operates on a constituent rather than the FlexGroup name. Use the constituent named by the EMS event, such as `fg__0024`.

=== Inspect the companion index

Diagnostic `volume explore` can expose the directory inode's `index-inode` pointer and the B+tree, but it is a diagnostic interface intended for NetApp personnel. It is not required for routine maxdirsize monitoring.

== Directory indexing in ONTAP

=== Why indexing exists

Without a persistent index, finding a name can require reading many directory blocks and building an in-memory hash. Beginning with ONTAP 9.2, ONTAP automatically creates a companion directory-index inode when a directory grows to approximately 2 MiB.

The persistent B+tree index maps a name hash and directory cookie to the location of the entry in the directory file. A targeted lookup can therefore read the required index and directory blocks instead of loading the entire directory. Indexing generally reduces CPU, memory, and I/O for lookup-oriented operations on large directories.

There is no administrator option to enable directory indexing. Crossing the threshold, an indexing scanner, or a qualifying front-end operation triggers it automatically.

=== What indexing does not change

The index is separate from the directory file:

* `maxdirsize` still limits the directory file.
* The companion index consumes additional metadata and an inode.
* Indexing improves targeted lookup more than full enumeration.
* Wildcard scans and `READDIR` still process the directory namespace.
* Losing or rebuilding the index does not remove the directory's names; ONTAP can reconstruct it from the directory file.

=== Private and public index inodes

By default, directory indexes historically reside in private inode space. ONTAP 9.17.1 introduced `-is-dir-index-transfer-enabled`. When set to `true`, new indexes are created in public inode space and a scanner migrates existing private indexes so supported SnapMirror and SnapMirror Cloud workflows can transfer them.

`-has-dir-index-public` is a read-only status field indicating that at least one public directory index exists. It is not the enable switch.

Public directory indexes count toward `files` and can increase `files-used` by approximately one inode for each indexed directory. Private indexes do not consume the public `files` allowance.

Enable index transfer when preserving indexes through replication or restore avoids expensive rebuilds for high-file-count directories. When transfer is disabled, SnapMirror omits private indexes and ONTAP rebuilds them on demand through a scanner or qualifying front-end operation. Do not enable transfer merely to improve local lookup performance; local indexing already occurs when the option is `false`.

== Sparse directories and hole punching

A directory can grow large and then become sparse after many names are deleted. The directory-file size remains at its high-water mark, so a naive `READDIR` could spend substantial CPU and I/O traversing empty blocks.

For indexed directories, ONTAP can punch a hole when a 4 KiB directory block becomes completely empty. The index tracks the hole so that:

* `READDIR` can skip the empty block.
* The physical block can be reclaimed.
* A later create can reuse that logical location.

The advanced `-has-optimized-sparse-directories` field is read-only status. A value of `true` means that the volume contains directory blocks in this optimized, hole-punched form. It is not a `volume modify` option and is not something an administrator enables as a goal.

If an application's directory remains operationally problematic after deletion, copying the remaining entries into a newly created directory produces a compact directory-file layout. Lowering `maxdir-size` does not compact a sparse directory.

== Capacity impact

Changing the `maxdir-size` setting consumes no capacity by itself. Actual growth does:

* The directory file allocates 4 KiB blocks as names are added.
* The companion index allocates separate B+tree and indirect blocks.
* Snapshot copies can retain older directory and index blocks.
* A directory that reached a high-water mark can keep its logical size after deletion.

For example, authorizing a 4 GiB cap does not allocate 4 GiB. A directory that actually grows to approximately 4 GiB has consumed roughly that amount in directory-file blocks, plus its index and other metadata overhead.

Do not include the data bytes of files below the directory when estimating `maxdirsize`. Include directory and index overhead in overall volume and aggregate capacity planning.

== Performance impact

Large directories can affect:

* Name lookup, create, unlink, and rename path length
* Full directory enumeration and wildcard searches
* CPU and memory used for namespace processing
* Cold-cache I/O needed to load index and directory blocks
* Protocol latency and client timeouts during long operations
* Namespace scans performed by analytics, backup, replication, or security features

Directory indexing reduces targeted-lookup cost, but it does not make a very large flat directory equivalent to a sharded hierarchy. Operations against a single directory can still encounter serialization and affinity limits even when the surrounding volume or cluster has unused resources.

Raise `maxdir-size` only when the workload requires a larger single directory and restructuring is not practical. Prefer a wide or deep hierarchy when the application permits it.

== What happens when maxdirsize is exceeded?

When a directory file reaches the cap:

* ONTAP rejects operations that need to add another name to that directory.
* The client can report ENOSPC, "file too large," NFS error 27, `STATUS_CANNOT_MAKE`, or another application-specific create or rename failure.
* Other directories can continue to accept entries if they have capacity and inodes.
* The volume can still have free data capacity and public inodes.
* Reading existing files is not equivalent to adding another directory entry and is generally unaffected.

Deleting entries can expose reusable directory slots, but it does not reduce the high-water directory-file size. The durable fix is usually to distribute names across new directories. If the flat namespace cannot change, evaluate a controlled `maxdir-size` increase:

----
set -privilege advanced
volume modify -vserver <svm> -volume <volume> -maxdir-size 327MB
----

For average growth, public guidance recommends increasing the current cap in increments of approximately 2%. For a migration with a known measured requirement, set the cap approximately 2% above that requirement. The change is immediate. You can later lower the cap, but not below the largest existing directory-file high-water mark; lowering it does not compact existing directories. Validate the supported value for the ONTAP release and platform, and monitor performance after the change.

== FlexVol and FlexGroup considerations

=== FlexVol volumes

A FlexVol has one file system and one public inode supply. `maxdirsize` still applies independently to every directory. A single hot directory is processed within that volume's ownership and does not gain parallelism merely because the cluster contains additional nodes.

=== FlexGroup volumes

A FlexGroup presents one namespace backed by multiple FlexVol constituents. This improves aggregate file-count scale and enables distribution across nodes and aggregates, but it does not multiply the limit of one logical directory by the constituent count.

Consider the following differences:

* Directory entries can point to files on remote constituents and can require a larger on-disk representation than local FlexVol entries.
* The same visible filenames can therefore consume directory-file space at a different rate than in a FlexVol.
* File and inode capacity is maintained per constituent, so distribution and constituent pressure matter.
* Modify `maxdir-size` on the FlexGroup, not directly on a constituent.
* Sharding an application across multiple directories gives ONTAP more opportunities to distribute work and files.

Do not assume that a FlexVol files-per-directory estimate transfers unchanged to FlexGroup. Include the volume type in every maxdirsize model or migration assessment.

== ONTAP functionality and enhancements related to maxdirsize

[options="header"]
|===
| ONTAP release | Functionality

| ONTAP 9.2
| Added persistent indexing for directories at approximately 2 MiB, reducing the need to load an entire large directory for targeted lookup.

| ONTAP 9.5 (documented)
| The ONTAP 9.5 command reference includes `-has-optimized-sparse-directories`, establishing that optimized sparse directories are supported by this release. The optimization hole-punches fully empty blocks in indexed directories so `READDIR` can skip holes and physical blocks can be reclaimed. Available public documentation does not identify whether an earlier ONTAP 9 release introduced it.

| ONTAP 9.14.1
| Public guidance identifies 320 MiB as the default `maxdir-size`. Published guidance commonly describes increases up to approximately 1 GiB and cautions about higher settings. Supported maximums remain release- and platform-dependent; verify Hardware Universe and support guidance.

| ONTAP 9.17.1
| Added `-is-dir-index-transfer-enabled` and public directory-index inodes so supported replication and restore workflows can transfer indexes instead of rebuilding them.

| ONTAP 9.20.1 (internal target; uncommitted)
| Internal planning targets first-class enablement and performance work for directories up to an older 4 GiB on-disk ceiling. This is not a customer support statement or release commitment. Do not plan a production directory above the currently published supported maximum until ONTAP release documentation and Hardware Universe explicitly qualify it.
|===

Do not present uncommitted future work as available functionality. Use the release notes, Hardware Universe, and command reference for the target ONTAP release as the final support authority.

== Volume options related to large directories

[options="header"]
|===
| Field | Settable and privilege | Purpose

| `maxdir-size`
| Yes, advanced
| Authorizes a larger per-directory file. Raise only after measuring or modeling need.

| `is-dir-index-transfer-enabled`
| Yes, admin
| Moves directory indexes into public inode space for supported replication and restore portability. It does not enable indexing.

| `has-dir-index-public`
| No, advanced
| Reports whether public directory-index inodes exist.

| `has-optimized-sparse-directories`
| No, advanced
| Reports whether the volume contains optimized hole-punched sparse directories.

| `language`
| Limited, admin
| Controls name interpretation. Non-ASCII and alternate name forms can change directory packing.

| `analytics-state`
| Yes, admin
| Enables File System Analytics. Its namespace scans add work on high-file-count volumes but do not change `maxdirsize`.
|===

== EMS messages related to maxdirsize

=== `wafl.dir.entries.warning`

The number of occupied directory entries has crossed the configured warning percentage. Use the volume and file ID to locate the directory, then evaluate its entry count, current directory-file size, and growth pattern.

=== `wafl.dir.size.warning`

The directory has reached the configured warning percentage, typically 90%, of its `maxdirsize` limit. Use the volume and file ID from the event to resolve the directory path. Restructure the namespace or plan an increase before the cap is reached.

=== `wafl.dir.size.max.warning`

The directory has reached or exceeded the configured warning percentage, typically 90%, while the volume's current `maxdirsize` is below the default value defined by the release (the EMS reference describes that default as 1% of system memory). This differs from the normal `wafl.dir.size.warning` condition. Determine why the configured cap is below the default before deciding whether to restore the default, restructure the directory, or choose another supported value.

=== `wafl.dir.size.max`

The directory reached `maxdirsize`. Operations that add names fail until slots become reusable, the namespace is restructured, or the limit is raised.

=== `wafl.maxdirsize.boot.notice`

At boot, ONTAP emits this NOTICE for a volume whose configured value is higher than the default. It reminds the administrator that operations on very large directories can carry a performance penalty.

=== Sparse `READDIR` events

`wafl.readdir.expired` and `wafl.readdir.sparse` identify expensive enumeration of large sparse directories. They are related to directory layout and high-water behavior, but they do not mean that `maxdirsize` itself has been reached.
